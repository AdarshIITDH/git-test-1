# Diagnose and Fix Empty SUSE GenAI Observability Views

SUSE AI Observability Extension version 2.2.0 is installed and working.

Current confirmed state:
- GenAI sidebar is visible.
- GPU Nodes shows NVIDIA L40S-16Q in Ready state.
- Kubernetes monitoring works for `observability` and `coding-assistant`.
- DCGM GPU utilization and framebuffer metrics are already collected.
- AI Applications, Inference Engines, LLM Models and All GenAI Components are empty.
- vLLM and LiteLLM are running on `coding-assistant`.

Your objective is to **identify the exact reason the remaining GenAI views are empty, then safely fix the missing monitoring configuration**.

## Environment

Codex execution: Rancher Management VM.

Observability downstream kubeconfig:
`/root/observability-deployment/downstream.kubeconfig`

Coding Assistant downstream kubeconfig:
`/root/coding-assistant-aif-migration/kubeconfig.json`

Observability UI:
`https://observability.demo.local`

Existing GenAI release:
`ai-obs`, namespace `so-extensions`, chart version 2.2.0.

## Phase 1 — Root Cause Analysis (Read-only)

1. Inspect the existing SUSE AI StackPack topology synchronization, GPU entity discovery and component mappings.

2. Discover the actual vLLM Service, namespace, port, model name, image version and `/metrics` endpoint on `coding-assistant`.

3. Verify whether vLLM exports real Prometheus metrics such as:
   - `vllm:num_requests_running`
   - `vllm:num_requests_waiting`
   - `vllm:prompt_tokens_total`
   - `vllm:generation_tokens_total`
   - TTFT and end-to-end latency histograms

   Adapt to actual metric names.

4. Check existing ServiceMonitor resources and OTel scrape configuration. Determine whether vLLM is currently scraped.

5. Query the SUSE Observability metrics backend for actual vLLM metrics. Distinguish:
   - Endpoint not exposing metrics.
   - Scrape target not discovered.
   - Collector scrape failure.
   - Metrics not reaching server.
   - Metrics reaching server but missing GenAI topology identification.

6. Inspect SUSE AI extension 2.2.0 topology mappings and compare observed resource attributes with:
   - `suse.ai.component.name`
   - `suse.ai.component.type`
   - `k8s.cluster.name`
   - `k8s.namespace.name`
   - `service.name`
   - `gen_ai.provider.name`
   - `gen_ai.request.model`

7. Examine whether existing Coding Assistant or LiteLLM telemetry emits the GenAI metrics and traces required for AI Applications and LLM Models.

8. Check whether the vLLM metric name normalization from `vllm:` to `vllm_` is required by the installed collector and extension.

9. Produce a concise table showing each blank GenAI view, its missing data or topology mapping, and the confirmed root cause.

Do not infer success from Kubernetes pod status alone.

## Phase 2 — Fix Inference Engine Monitoring

Once the cause is identified:

1. Reuse the existing SUSE Observability Agent and OpenTelemetry scraping pipeline.

2. If vLLM scraping is missing, create a dedicated ServiceMonitor targeting its existing Service and `/metrics` endpoint.

3. Preserve the existing GPU/DCGM ServiceMonitor.

4. Configure the documented version-compatible metric name normalization and SUSE AI resource attributes, if required, using a monitoring-only collector configuration.

5. Preserve cluster and namespace identity in all telemetry.

6. Verify vLLM metrics reach the server.

7. Verify that vLLM appears under GenAI Observability → Inference Engines.

8. Verify the engine's actual performance metrics and relevant available charts.

## Phase 3 — Fix LLM Model Discovery

1. Inspect how SUSE AI Extension 2.2.0 identifies LLM models.

2. Verify the exact served model identifier from vLLM `/v1/models`.

3. Check whether `gen_ai.request.model` is being emitted by existing instrumentation.

4. If model telemetry can be obtained through existing non-disruptive monitoring components, configure the appropriate supported OTel inference/model topology mapping.

5. Never fabricate model metrics or create synthetic successful requests.

6. Verify the real model appears under LLM Models.

If model discovery requires changes to running application processes, document the necessary instrumentation and do not restart those applications without approval.

## Phase 4 — Diagnose AI Application Discovery

Inspect the Coding Assistant and LiteLLM telemetry.

Determine whether they emit:
- GenAI request counts
- Input/output token metrics
- Request model/provider attributes
- OTel application/resource identity
- GenAI request traces

Compare against the SUSE AI Extension's requirements.

If AI Applications requires OpenLIT, OpenTelemetry SDK or equivalent instrumentation that would require changing/restarting the running application, DO NOT perform that disruptive change.

Instead, produce a precise, minimal implementation plan to instrument the application during a later maintenance window.

## Phase 5 — Validate

Verify:

- Existing GPU Nodes remains functional.
- Both Kubernetes clusters remain observed.
- Inference Engines displays vLLM if supported telemetry and mappings are available.
- LLM Models displays the real model where discovery requirements can be met non-disruptively.
- AI Applications only displays components supported by actual instrumentation.
- Existing Coding Assistant application remains accessible.
- vLLM and LiteLLM have not been restarted.
- No change to GPU Operator, DCGM Exporter or Observability Server.
- No duplicate telemetry scraping.

Report:
1. Confirmed root cause for each missing view.
2. Changes applied.
3. Exact metrics collected.
4. Which GenAI sections now contain real data.
5. What instrumentation is still necessary.
6. Actual UI verification results.

**Execution behavior:** Complete read-only diagnosis first, then execute safe monitoring-only fixes. Do not reinstall the existing extension or monitoring stack. Do not stop for routine missing monitoring resources. Stop only if a fix requires restarting or modifying existing applications, or if essential authorized access is unavailable.
